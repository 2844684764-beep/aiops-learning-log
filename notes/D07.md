## 二、踩坑与破局（Troubleshooting）

> "纸上得来终觉浅，绝知此事要躬行。" 本周最大的收获来自于那些报错和排错的过程。

### 1. 网络延迟注入失效之谜（`tc netem` 坑）

- **现象**：使用 `tc` 命令在 `ens33` 网卡注入 200ms 延迟，但在本机执行 `curl` 测速依然秒回，延迟未生效。
- **排查与根因**：
  - 查阅 Linux 网络栈机制发现，本机访问本机 IP 时，内核直接走回环接口（`lo`）处理，数据包根本不经过物理网卡 `ens33`。
  - 此外，`netem` 默认只作用于出站（egress）流量，无法直接限制入站（ingress）。
- **解决**：
  - 明确测试边界：测本机服务需将延迟规则加在 `lo` 网卡上；若测跨机访问，则使用外网地址（如百度）或从另一台机器发起请求。
  - 熟练掌握了 `tc qdisc replace` 覆盖冲突规则，并在测试结束后使用 `tc qdisc del` 彻底清理环境，避免影响后续实验。

### 2. Alertmanager 与 Receiver 的断联

- **现象**：重启 uvicorn receiver 后，再次制造故障，却发现终端收不到告警弹窗了。
- **排查与根因**：Prometheus 的告警状态具有时效性（重启后 `for` 计时清零），且通过排查发现 `curl` 缺少了 `-k` 参数导致静默失败。接口在告警恢复后正常返回空数据。
- **解决**：通过 `curl` 分段排查 `/api/v1/alerts` 与 `/api/v2/alerts` 接口，理清了 `Pending -> Firing -> Resolved` 的流转逻辑。养成将 receiver 放入后台（`nohup`）并输出到 `alerts.log` 的习惯，方便持续追踪。

> **补充核对（写复盘时补的）**：`-k` 只影响 HTTPS 的证书校验，对 `http://host.docker.internal:8001` 这种明文请求不起作用。
> 更可能的真因是两条叠加：**① receiver 是前台进程，重启后没再起来**（`ss -tlnp | grep 8001` 没输出）；
> **② Prometheus 的 `for` 计时在重启后归零**，必须重新累计满 `for` 的时长才会再次 firing。
> 面试讲这个案例时，用这两条更站得住。

### 3. Docker Compose 挂载与 YAML 语法

- **现象**：修改 `prometheus.yml` 挂载 `rules.yml` 时报错，容器无法启动。
- **解决**：明确了 YAML 严格依赖空格缩进的语法（禁用 Tab），以及挂载配置文件时使用 `:ro`（只读权限）的最佳实践，避免容器内部误改宿主机文件，同时确保宿主机上存在对应的实体文件，防止 Docker 自动创建同名目录。

## 三、认知升级与方法论

- **排障三步曲**：不再盲目重启，而是遵循 **"观察指标 (top/df) → 定位进程 (ps/iotop) → 查看日志 (journalctl/docker logs)"** 的标准流程。
- **监控的本质是"发现异常"**：告警规则不能拍脑袋，必须结合真实的业务指标（如 P95 延迟、错误率）来设定阈值，并考虑到告警风暴的收敛。
- **文档沉淀习惯**：整理了属于自己的 `cheat sheet`，将临时记住的命令固化为长期能力。

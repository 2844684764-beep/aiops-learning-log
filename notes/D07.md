## 一、三个问题

### Q1：从「用户请求」到「我在 Grafana 看到曲线」，中间经过哪几步？

1. `traffic.sh` 每 2 秒 `curl localhost:8000/` 和 `/slow`
2. uvicorn 收到请求 → `AccessLog` 中间件记录一条 JSON 日志（trace_id、latency_ms）→ 同时给 `Counter` / `Histogram` 加值
3. Prometheus 每 15 秒访问 `host.docker.internal:8000/metrics`，把数字写进时序数据库
4. Grafana 用 PromQL 向 Prometheus 的 HTTP API 查询（`rate()`、`histogram_quantile()`）
5. 浏览器渲染成曲线

**关键理解**：中间件写日志、Prometheus 抓指标、Grafana 查询，是**三条独立的路径**。日志和指标不是一回事——日志是给人看细节的，指标是给机器算趋势的。

### Q2：P95 突然涨到 2 秒，第一步看什么？第二步？

**第一步：确认是不是真的慢**

- QPS 有没有突变（流量涨了自然会慢）
- 日志里 `latency_ms` 的分布：是全部变慢，还是只有某几个请求慢
- 是不是压测脚本刚好打到了 `/slow`

**第二步：分清「自己慢」还是「等别人慢」**

| 看什么 | 命令 | 说明 |
|---|---|---|
| CPU / 内存 | `top` | `us` 高 = 自己在算；`wa` 高 = 在等 IO |
| 磁盘 | `iostat -x 1` | `%util` 接近 100 或 `await` 很高 = 磁盘瓶颈 |
| 下游依赖 | 日志里的耗时拆解 | 本地处理快、下游慢 |
| 网络 | `ss -tn`、`ping` | 连接数暴涨、重传 |

**第三步：看变更**

最近有没有发布、改配置、扩容？故障时间点前后 10 分钟发生了什么？

> 这一套顺序的价值：**先确认问题存在，再缩小范围，最后才猜原因**。反过来的话，容易一上来就怀疑某个组件，然后花半小时验证一个错误假设。

## 四、这一周踩过的坑（面试可讲）

| # | 坑 | 一句话 |
|---|---|---|
| 1 | Grafana 面板编辑器 `insertBefore` 崩溃 | 前端 bug，改用文件供给（provisioning） |
| 2 | 容器 uid 472 读不到宿主机目录 | 容器用户 ≠ 宿主机用户，需 `chmod 711` + `a+rX` |
| 3 | 带标签的指标重启后消失 | 没有流量就没有子指标，`/metrics` 空是正常的 |
| 4 | 8000 端口杀不死 | `Restart=always` → 用 `systemctl`，别 `kill` |
| 5 | ens33 加延迟测不出 localhost | `tc` 只对 egress 生效，localhost 走 `lo` |
| 6 | 2G 文件只占 6% | 36G 的分母，先算比例再怀疑工具 |

## 五、这一周真正学会的东西

1. **可观测性三件套的分工**：指标看趋势、日志看细节、告警代替人盯屏
2. **Pull 模型**：Prometheus 主动来抓，所以服务必须一直活着
3. **P95 比平均值有用**：平均值会被少量极慢请求掩盖
4. **容器边界**：容器的 `localhost` 不是宿主机的 `localhost`
5. **systemd 是双刃剑**：`Restart=always` 既保自愈，也让人误以为「杀不死」
6. **爆炸半径意识**：能在小容器里炸，就别炸系统盘

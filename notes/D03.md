## 今天卡住的两个问题

### 问题 1：8000 端口一直被占用，杀一个又冒一个

**现象**：`kill` 掉 uvicorn 后，3 秒内又出现一个新的占用 8000 端口，PID 还变了。

**排查**：

```bash
ss -tlnp | grep 8000
# users:(("uvicorn",pid=8026,fd=7))

ps -o pid,ppid,user,args -p 8026
# 8026  1  shawny  .../uvicorn app:app ...

systemctl show aiops-app -p NRestarts
# NRestarts=3        ← 杀了 3 次的记录
```

**原因**：**父进程是 1（systemd）**，因为 `aiops-app.service` 里配了：

```ini
Restart=always
RestartSec=3
```

只要进程不是被 systemd 主动停的，3 秒后就自动拉起。

**结论**：这不是 bug，是守护进程在正常工作。

**正确做法**：

```bash
sudo systemctl restart aiops-app   # 改完代码
sudo systemctl stop aiops-app      # 要手动接管时
```

**判断口诀**：端口被占 + 父进程是 1 = systemd 管着 = 别 kill，用 systemctl。

### 问题 2：日志里的 `client` 为什么全是 127.0.0.1

**现象**：603 条日志，`client` 全是 `127.0.0.1`。

**原因**：

1. 唯一的流量源是 `aiops-traffic.service`，它执行 `traffic.sh localhost:8000`——请求走本机回环网卡，对端自然就是 `127.0.0.1`
2. `client` 取的是 `request.client.host`，即 **TCP 连接的对端 IP**，不是 HTTP 头里的信息
3. Prometheus 的请求被中间件跳过了，所以看不到 Docker 网桥地址（`172.18.0.1`）

**验证方法**：从 Windows 访问一次，日志会出现 `192.168.223.1`：

```powershell
curl.exe http://192.168.223.129:8000/slow
```

注意它不是你的 Windows IP，而是 **VMware NAT 的网关**——虚拟机经过 NAT 只能看到网关。

## 一个重要的延伸：真实 IP 会丢

生产环境里服务前面通常有 Nginx / 负载均衡：

```
用户 → Nginx/LB → 服务
```

此时 `request.client.host` 会变成代理的 IP，所有日志都是同一个地址，**真实用户 IP 丢失**。

解法是读代理写入的头：

```python
client_ip = (
    request.headers.get("x-forwarded-for", "").split(",")[0].strip()
    or request.headers.get("x-real-ip")
    or (request.client.host if request.client else "-")
)
```

但有个前提：**只有来自可信代理的请求才能采信这个头**。客户端可以自己伪造 `X-Forwarded-For`，直接信任等于让人随便伪装 IP 绕过限流。

## 今天真正理解了什么

- **日志要能被程序读**：正则提取想死，`jq` 一行搞定
- **trace_id 是串联的钥匙**：一次用户操作可能打多个服务，靠它把散落的日志连起来
- **`client` 是 TCP 层的事实，`X-Forwarded-For` 是应用层的声明**，前者可信但不能穿透代理，后者能穿透但可能被伪造
- **systemd 的 `Restart=always` 是双刃剑**：既保证服务自愈，也让人误以为「杀不死」

## 代码小瑕疵（不影响运行）
